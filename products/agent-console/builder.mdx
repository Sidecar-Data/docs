Builder is Sidecar's engineering agent. Give it a well-scoped task — add tests, fix documentation, build a model — and it researches your repositories, makes the change, validates it, and delivers a branch or pull request for your team to review. Builder is the first agent available in the [Agent Console](/products/agent-console/overview).

## What Builder is good at

Builder is trained on analytics engineering workflows and ships with skills for designing data models, onboarding data sources, and shipping dbt changes. Typical jobs include:

- **Testing and documentation** — add primary-key and schema tests, audit test coverage, fix documentation that has drifted from model logic, add source freshness checks, clean up orphaned YAML entries
- **Model development** — build staging, intermediate, and mart models, implement snapshots for slowly changing dimensions, write or refactor macros
- **Refactoring** — split monolithic models into layers, consolidate duplicated marts, rationalize inconsistent logic
- **Source onboarding** — declare sources in YAML, wire up freshness checks, scaffold the staging layer for a new source
- **Analysis** — audit or investigate without changing code; the result comes back as a written answer on the run

Builder works with the context Sidecar already has about your stack, so instructions can reference your models and sources the way your team talks about them.

## How Builder delivers changes

Builder follows a strict delivery contract designed for review-first teams:

1. It works on a dedicated git branch per repository, always prefixed `sidecar/`. It never commits to your default branch.
2. Commits are authored as `Sidecar Builder`, so agent changes are unmistakable in history.
3. Depending on the job's **Delivery** setting, Sidecar either opens a pull request from the pushed branch (the default) or records the branch with a compare link and opens no pull request.
4. If the job's approval policy requires it, the run pauses for a human decision before the pull request is opened.
5. **Builder never merges.** It cannot merge changes, enable auto-merge, bypass branch protection, or approve its own work. Review and merge always stay with your team, and the pull request body says so.

## Quickstart: your first Builder run

### Before you start

You need:

- A Sidecar workspace with the Agent Console enabled
- The Sidecar GitHub App installed (or GitLab connected) with access to at least one repository

<Steps>
  <Step title="Open Builder">
    In Sidecar, go to **Agents** and open the **Builder** tab.

    Check the **Scope** section — it lists the repositories Builder can access. If it's empty, connect a source-control integration first via **Manage integration**.

  </Step>

  <Step title="Create a job">
    Click **New job** and fill in the form:

    - **Name** — for example `Primary key tests`
    - **Description** — optional, shown in the jobs table
    - **Instructions** — what Builder should do on each run (see the examples below)
    - **Repositories** — leave empty to use all of Builder's repositories, or pick the one this job targets
    - **Delivery** — keep **Open a pull request** for this first run

    Click **Create job**. You land on the job's configuration page, where you can refine any of these settings later.

    <Frame caption="A job captures the instructions, scope, and delivery settings for a repeatable task.">
      <img
        src="/images/agent-console/new-job-dialog.png"
        alt="New job dialog with name, description, instructions, repository picker, and delivery mode fields"
      />
    </Frame>

  </Step>

  <Step title="Run it">
    Click **Run now**. The run opens in the Console and moves from **Queued** to **Running**.

    Watch progress on the run detail page — expand a turn to see Builder's messages and tool calls as it researches the repository and makes the change.

  </Step>

  <Step title="Approve the pull request gate">
    With **Require approval** on (the default), the run pauses at **Awaiting approval** before the pull request is opened. The approval panel shows the repository, branch, and title Builder proposes.

    Click **Approve** to let Sidecar open the pull request, or **Reject with note** to tell Builder what to do instead — it will adjust without opening the pull request.

  </Step>

  <Step title="Review and merge">
    When the run reaches **Succeeded**, the pull request appears under **Artifacts**. Open it, review the change like any other pull request, and merge when your team is satisfied.
  </Step>
</Steps>

## Writing good instructions

Builder does its best work when a job reads like a well-written ticket:

- **Name the target.** Reference the repository (or set the job's scope), and the models, sources, or paths involved.
- **State the outcome.** Say what done looks like — tests added, docs corrected, a model built and documented.
- **Set boundaries.** One coherent task per job. Say what's out of scope if the surrounding code is messy.
- **Ask for analysis explicitly.** If you want an investigation without code changes, say so — the result arrives as an answer artifact instead of a branch.

Example instructions for common jobs:

```text Add primary key tests
Review the mart models in models/marts/ and add missing primary-key tests
(unique + not_null on the id column) to their YAML. Don't change model SQL.
```

```text Fix documentation drift
Compare the column descriptions in models/marts/core/_core__models.yml against
the actual model logic and fix any descriptions that are wrong or outdated.
```

```text Build a new mart
Build a location_sales mart that aggregates order revenue by store location and
month, following our existing mart conventions. Include YAML with tests and
column descriptions.
```

```text Test coverage audit (analysis only)
Audit test coverage across our dbt project and report which models lack
primary-key tests, ranked by number of downstream dependencies. Do not make
any code changes.
```

## Guardrails

- **Scoped access.** Builder can only reach repositories your source-control integration grants, and each job can narrow that further.
- **Branch-only changes.** All work lands on `sidecar/` branches — never directly on your default branch.
- **Human approval.** Gated actions pause for your decision when the job requires approval; auto-approved actions are still recorded for audit.
- **No merging, ever.** Merge decisions belong to your team.
- **Full audit trail.** Every run keeps its instructions, turn-by-turn transcript, approval decisions, and delivered artifacts — even after the job is deleted.

## Troubleshooting

- **Run now is disabled** — the job is paused. Switch its Active toggle on.
- **"Already running" when starting a run** — each job runs one execution at a time; the message links to the active run.
- **Run failed** — open the run detail page; the error is shown at the top. A common cause is a repository in the job's scope that the integration can no longer access.
- **No repositories in Scope** — install the Sidecar GitHub App (or connect GitLab) and grant it the repositories Builder should work on. The scope updates automatically.
