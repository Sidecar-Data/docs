# Sidecar monitors as code

Sidecar creates monitors from definitions in the dbt project. Two locations, one schema:

1. Model YAML under `config.meta.sidecar` (never top-level `meta`). Reaches Sidecar via the production dbt run.
2. `sidecar/monitors.yml` at the repo root. Reaches Sidecar from Git on merge. Use it for many models at once or for package models whose YAML is not in the repo.

Identity is `<model>::<key>`. A new key is a new monitor; a new `name` is not. Never define the same key for a model in both locations.

## Model block

```yaml
models:
  - name: fct_orders
    config:
      meta:
        sidecar:
          version: 1
          defaults:                 # optional, applies to all monitors below
            schedule: { cron: "0 * * * *" }
          monitors:
            orders_volume:          # key: ^[a-z][a-z0-9_]{0,63}$
              type: volume
              sensitivity: medium
            orders_freshness:
              type: freshness
              freshness_threshold: { hours: 6 }
            orders_negative_revenue:
              type: custom
              name: Orders with negative revenue
              sql: |
                SELECT order_id FROM [[ this ]] WHERE net_revenue < 0
              fail_when: { operator: gt, value: 0 }
              investigation_instructions: Check recent pricing and refund changes.
```

## Repository file

```yaml
version: 1
defaults:
  schedule: { cron: "0 */6 * * *" }
models:
  - name: fct_orders                # or unique_id: model.<project>.fct_orders
    defaults:
      schedule: { cron: "30 * * * *" }
    monitors:
      orders_volume: { type: volume, sensitivity: high }
```

Defaults apply file → entry → monitor. Use `unique_id` for ambiguous or package models.

## Types

**custom**: `sql` (required) is one SELECT returning the offending rows; Sidecar counts them. `fail_when` (required): `operator` in `gt gte lt lte eq neq`, integer `value`; fails when `count <operator> value`. Reference tables only as `[[ this ]]` or `[[ ref('model') ]]`; no `{{ }}`, no hard-coded names, no DDL/DML, no multiple statements, no trailing semicolon. Warehouse SQL dialect, no dbt macros. Referenced models must be in the warehouse the Sidecar source runs custom SQL on.

**volume**: `sensitivity` in `low medium high` (default `medium`). Model must be materialized as a table.

**freshness**: `freshness_threshold` (required) with `days` and/or `hours`, at least one above zero. `freshness_mode`: `row_count_change` (default) or `last_updated` (not on Redshift). Table materialization required.

## Common fields

- `name`: display name; defaults to the key.
- `schedule`: `{cron: "..."}` (15 min minimum), `{mode: interval, every_hours: 1|2|3|4|6|8|12, days_of_week: [...]}` (Monday = 0), or `{mode: specific_hours, hours: [...], days_of_week: [...]}`. Integers only; `true` and `1.0` are rejected. Every monitor needs a schedule from itself, its defaults, or the Sidecar source.
- `notification_destinations`: `{type: slack, channel_id, channel_name}` or `{type: email, email}` on the company domain. Omit for source defaults.
- `investigation_instructions`: short runbook for the Reliability agent on failure.

No other fields. Unknown fields block the definition. There is no `enabled`; pausing happens in the Sidecar UI.

## Edits

- Threshold, SQL, schedule, name: edit in place; history is kept.
- Rename: change the key; Sidecar moves the monitor if its table (volume, freshness) or SQL (custom) is unchanged.
- Remove: delete the block; the monitor is retired, runs are kept.
- Type or table change: blocked. Delete and add under a new key.

## Checklist

Keys valid and unique per model. `version: 1` present. References are `[[ this ]]` / `[[ ref() ]]` and columns exist. Each monitor resolves a schedule. YAML parses under `config → meta → sidecar`.

After merge the user runs **Observability → Monitors → Sync from dbt**; model blocks also need a production dbt run first. A blocked definition's error code names the rule above that was broken.
